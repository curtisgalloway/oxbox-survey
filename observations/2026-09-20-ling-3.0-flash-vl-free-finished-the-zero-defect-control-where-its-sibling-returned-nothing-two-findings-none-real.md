# ling-3.0-flash-vl:free finished the zero-defect control where its sibling returned nothing — two findings, none of them real

**What happened** — the experiment the ask-grounding row could not do. The
sibling `ling-3.0-flash-fin:free` spent its entire cap reasoning on this
fixture on 2026-09-08 and returned nothing; the vision variant finished inside
the v2 cap with a real answer. It then emitted two findings on a file whose
expected count is zero: one true observation whose defect status needs the
editor, and one invented race.

## Evidence

```
oxbox-send: venue=openrouter model=inclusionai/ling-3.0-flash-vl:free mode=review effort=medium context=6096B files=1
oxbox-send: finish=stop prompt_tokens=1932 completion_tokens=7993 reasoning_chars=28961 route=Novita
```

`finish=stop`, `truncated: false`, 7,993 of the fixture's 16,000-token cap. The
sibling's failure does not repeat.

**Finding 1 — `dns_lookup` has no timeout.** Scored **unresolved**, not real
and not invented.

The code claim is true. At `6302b12:jailtest.py`, `tcp_connect` (line 79) and
`udp_send` (line 89) both call `sock.settimeout(5)`; `dns_lookup` is two lines
with a bare `socket.getaddrinfo("example.com", 443)` and no bound. Nothing is
fabricated and the inconsistency is real on the page.

What it does not establish is that the gap is a defect. The probes exist to
raise immediately inside the jail, the hang it describes needs DNS blackholed
rather than refused, and nothing here reproduced that. The prescribed fix is
measurably wrong:

```
uncached getaddrinfo under socket.setdefaulttimeout(0.001):
gaierror after 0.018s -- 18x the budget, no timeout raised
```

`socket.setdefaulttimeout` bounds new socket objects, not the resolver, so the
suggested `setdefaulttimeout(5)` wrapper would not bound `getaddrinfo` at all.
A true observation with a non-working fix and an unreproduced hazard is exactly
what `unresolved` was added for on 2026-09-08 — it is not real, it is not
benign, and putting it in the false bucket would be wrong. **This is the first
`unresolved` in the record**, and it needs the editor's ruling.

**Finding 2 — TOCTOU between `os.path.isdir` and `open` in `read_probe`.**
Invented. A time-of-check race needs a concurrent mutator; this is a
single-threaded diagnostic run by hand inside a jail. The model labeled it
UNCERTAIN and argued in the same paragraph that it is "unlikely to be
exploitable in this context" — and then reported it as a numbered finding with
a Defect heading, which under the 2026-09-10 scored-as-written ruling is a
finding. It is the plausible-looking race the answer key's closing section
warns about.

Neither of the two known false positives appeared: the dead `REPO_ROOT`
binding and the unused `write_probe` were both left alone, and the closing
paragraph explicitly cleared resource management, error handling, scoring and
`EXISTING` gating.

## So what

The interesting number is the one that is not a finding count. The sibling's
empty return was the reason `answered: false` exists, and the v2 fixture's
16,000-token cap was set in response to models exhausting their budget on this
file. This variant used half of it and stopped. Same family, same venue, same
fixture, opposite outcome — so the empty return was the model, not the pool and
not the fixture.

On invention, two findings on a clean file is a middling result and the prior
art says to expect it: the key cites published precision around 0.5 on
defect-bearing code, and a high invention count here is the expected outcome
rather than a surprise. What separates this run is that both known traps were
declined and one of the two findings is a true statement about the code. That
is a better failure than inventing two races.

No rating is written here. One fixture, one run, and the fixture's own key says
to treat a clean-ish result as one data point against invention, never as a
license to skip verification.
