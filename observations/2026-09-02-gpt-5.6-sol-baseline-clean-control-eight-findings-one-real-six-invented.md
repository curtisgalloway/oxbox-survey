# GPT-5.6 sol baseline on the clean control: 8 findings emitted, 1 genuinely new and real, 6 inventions, 1 true and negligible

**What happened** — `oxbox-clean-control` (`jailtest.py` at `6302b12`, 6,096 B,
`--mode review`) put to `openai/gpt-5.6-sol`. Eight numbered findings, each with a
failure scenario, no UNCERTAIN section. One is real and was fixed in oxbox the
same hour: on a host with no route out, the three network probes raise for the
wrong reason and report PASS without testing anything. The three numbers the key
asks for: **emitted 8, genuinely new and real 1, inventions 6**, plus one true
observation that fails safe and is not worth a change.

## Evidence

Run `logs/2026-09-03T02-41-51Z`, `context_bytes` 6096, `finish_reason` stop.
Verified against `git show 6302b12:jailtest.py`, `6302b12:profiles/jail.sb` and
`6302b12:oxbox`.

| # | Finding | Verdict |
|---|---|---|
| 1 | A missing `OXBOX_EXISTING_PATHS` is treated like an empty list, so every filesystem probe skips and the script can exit 0 | **invention.** The skip is printed as `[SKIP] fs reads (oxbox reported no sensitive paths present)`, the launcher always sets the variable (`oxbox` line 352), and the file's own rule is that a probe that cannot test skips rather than answers. Working as designed and saying so. |
| 2 | Network probes treat every exception as enforcement; a host with no default route raises `ENETUNREACH`/`gaierror` and all three PASS | **real, and the more important of the two defects this fixture has now yielded.** Under bubblewrap `--unshare-net` the jail's own denial *is* `ENETUNREACH`, so no exception-type check can tell an offline host from a working jail from inside. By the docstring's standard — "passing by not looking" — the probes were vacuous offline. Fixed in oxbox `0090c35`: the launcher decides outside the jail whether a route exists (a UDP `connect()`, which sends nothing) and exports `OXBOX_HOST_HAS_ROUTE`; jailtest skips the three probes with a note when it is `0`. |
| 3 | `getaddrinfo` can succeed from `/etc/hosts`, reporting a DNS leak that is not one | **true, negligible.** Requires an `/etc/hosts` entry for `example.com`; the error is in the safe direction (a false FAIL, not a false PASS). Not changed. |
| 4 | UDP `sendto` success only proves the kernel queued it; a silent firewall drop reads as a leak | **invention** for this file. The probe measures whether the sandbox lets the syscall through, and `(deny network*)` makes it raise. A firewall downstream is a different system, and the direction is again a false FAIL. Sonnet raised the same point as UNCERTAIN. |
| 5 | `os.path.isdir` swallows the denied `stat`, so a directory the policy lets you list but not stat is opened instead and `IsADirectoryError` counts as blocked | **invention.** Same claim as Sonnet's first finding; the mechanism is accurate and the policy it needs — listing allowed, metadata denied — is not one either backend can express for a sensitive path (`jail.sb` allows `file-read*` per path, data and metadata together; bubblewrap does not bind the paths at all). |
| 6 | Metadata is tested only on `EXISTING[0]`; a `stat` leak on a later path goes unnoticed | **invention.** The oracle is a canary for one specific mistake, a global `file-read-metadata` allow (`jail.sb` lines 60–67 say so); that mistake is all-or-nothing. A per-path metadata leak would need a per-path allow rule that does not exist. A stat per path would be cheap and more thorough, but that is an improvement, not a defect. |
| 7 | `write_inside` uses a fixed filename, can truncate existing data, and can make a non-writable directory look writable | **invention.** The work dir is the sandbox's own scratch and `jailtest-ok.txt` is the test's own file; the second half needs a directory that forbids creating files while allowing a truncating open of one that already exists, which is not the sandbox's write policy. |
| 8 | No write probe against sensitive paths, so the standalone run cannot show they are unwritable | **invention**, the pre-registered one in a different coat. The comment block above `env_canary` explains why escape-write verification lives in `guardtest.py`: judged from inside, the two backends disagree. |

Completion 8,263 tokens, 7,534 of them reasoning. Half of Sonnet's spend on the
same file, with a real finding in it.

## So what

The clean control now has three baselines on it, and none produced the ideal
answer — an empty list with a short account of what was checked. Sonnet emitted 2
and found nothing new; Gemini emitted 1 and it was real; GPT emitted 8 and one was
real. Read as a calibration measurement, GPT's is the worst of the three: seven of
eight asserted defects with failure scenarios do not survive a reading of the
profile and the launcher, and there is no UNCERTAIN section to signal which ones
it doubted. Read as a discovery measurement, it is tied for best. Both readings
are what the fixture is for, and a free model's run here should be reported the
same way: emitted, real, invented, and whether it hedged.

The key's premise, "every defect anyone has found in it has been fixed at this
pin", is now false twice over. The pin stays frozen, the expected count stays
zero for the reason the key gives, and a future candidate that reports either
defect earns a real. Both are fixed at oxbox HEAD.

No marker: this is a baseline, not a candidate.
