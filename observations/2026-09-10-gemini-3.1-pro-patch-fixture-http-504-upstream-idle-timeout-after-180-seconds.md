# Gemini 3.1 Pro on the patch fixture: HTTP 504 "Upstream idle timeout exceeded" at 180 seconds, 1,908 completion tokens lost, nothing billed, and the resend answered

**What happened** — `oxbox-secret-scanner-fix` (`ox` at `6072d56`, 39,467 B,
`--mode diff`, effort high, 100,000 tokens, temperature 0.2) put to
`google/gemini-3.1-pro-preview`. At 180 seconds OpenRouter returned a
response whose choice carried `finish_reason` `error` and an error object,
code 504, "Upstream idle timeout exceeded", `error_type` `timeout`. The
usage block shows 10,537 prompt and 1,908 completion tokens consumed before
the cut, 7,533 characters of reasoning in flight, empty content, and
`cost` 0. The same payload re-sent four minutes later answered in 152
seconds and passed the fixture (its own observation).

## Evidence

Log `logs/2026-09-10T19-38-36Z`. From `response.json`:

```
"finish_reason": "error",
"error": {"code": 504, "message": "Upstream idle timeout exceeded",
          "metadata": {"error_type": "timeout"}},
"usage": {"prompt_tokens": 10537, "completion_tokens": 1908, "cost": 0,
          "cost_details": {"upstream_inference_cost": 0.04397}}
```

The reasoning text ends mid-thought ("I'm refining how keywords are matched
by adjusting the regex quantifiers"). `status.json`: `ok` false, `venue_cost`
null.

## So what

A frontier model on a first-party route can stall the same way the cheap
pools do, and the router gives up at three minutes of upstream silence
rather than at ox's 900-second read timeout. The bill was zero for the
failed attempt even though the upstream line shows 4 cents of inference. A
reader's script has to check the choice's `error` field and the content,
not the HTTP status, and plan a resend.

No disqualifier: the resend cleared it inside the hour.
