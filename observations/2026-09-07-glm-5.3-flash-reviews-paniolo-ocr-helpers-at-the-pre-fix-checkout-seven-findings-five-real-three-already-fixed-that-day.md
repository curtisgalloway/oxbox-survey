# GLM 5.3 Flash reviews paniolo's four OCR helpers at a stale checkout: seven findings, five real, three of them already fixed in the release cut that day

**What happened** — A real-project batch, not a fixture: `ocr/linuxocr`,
`ocr/rapidocr`, `ocr/visionocr.swift` and `ocr/winocr/src/main.rs` from
`curtisgalloway/paniolo`, 29,302 bytes, sent in review mode with a task
statement that described bounds-and-clipping changes as "just made". The
checkout the batch was read from was still at `6d48556`, twelve commits
behind the day's `main`, so the payload was the *pre-fix* code; the verifier
noticed the mismatch (`git log` on the files, clean working tree) and scored
the findings against the payload as sent.

## Evidence

Log `logs/2026-09-07T23-50-02Z` under the paniolo checkout: `finish_reason`
stop, not truncated, 7,715 prompt / 7,283 completion (5,809 reasoning),
76 s, $0.0024 billed. Verifier: a Sonnet 5 subagent that opened every file,
ran `_lines_from_tsv` directly, and executed two of the failure cases.

| # | claim | verdict | how settled |
|---|---|---|---|
| 1 | no bound on encoded input or decoded dimensions in any helper | CONFIRMED | read all four read/decode paths; nothing compares IHDR size to a limit before decode |
| 2 | winocr's `MaxImageDimension` guard runs after `GetSoftwareBitmapAsync` | CONFIRMED | decode at line 67, guard at 101-111 |
| 3 | linuxocr `to_source` clamps only at 0, so `min(w, src_w - x)` can go negative | CONFIRMED, reproduced | fed synthetic TSV rows across the pad boundary; `left=212` returned `[101, 5, -1, 5]` |
| 4 | linuxocr `_preprocess` catches only `ImportError`, so malformed bytes traceback | CONFIRMED, reproduced | `printf 'not a png' \| linuxocr - --json` with Pillow installed: raw `UnidentifiedImageError` |
| 5 | rapidocr unreadable input file raises uncaught `FileNotFoundError` instead of `die()` | CONFIRMED, reproduced | stubbed the heavy imports and ran `main` on a missing path |
| 6 | winocr never clips word-union bboxes to the image | present, impact UNCERTAIN | clipping code is absent; no evidence Windows OCR returns out-of-bounds rects |
| 7 | rapidocr `_reexec_into_venv` docstring disagrees with its code | CONFIRMED, cosmetic | re-execs whenever the venv exists, never checks importability |

Counted as real: 1 through 5. Not counted: 6 (defect in form, impact
unshown) and 7 (documentation). Nothing was refuted.

Findings 1, 2 and 3 are the three issues (#149, #150, #151) fixed in
paniolo PRs #163 and #164 and shipped in v0.1.19 later the same day; the
model found them independently and described the same mechanisms the
issue reports did. Findings 4 and 5 were not on the issue tracker and
still hold at v0.1.19.

## So what

At $0.0024 and 76 seconds the model re-derived a day's worth of human-filed
issues from the code alone and added two genuine ones, with zero false
claims in the batch. The verifier's job was mostly confirming, which is the
cheap direction. The lesson for the harness is about the checkout, not the
model: a review from a working tree that lags `main` reviews yesterday's
code, and the task statement's "just changed" premise did not match the
bytes sent. Read the target at a committed ref, as the corpus rules already
say.
