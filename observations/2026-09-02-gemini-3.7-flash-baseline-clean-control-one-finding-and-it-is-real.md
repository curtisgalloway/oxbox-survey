# Gemini 3.7 Flash baseline on the clean control: 1 finding emitted, 1 genuinely new and real, 0 inventions

**What happened** — `oxbox-clean-control` (`jailtest.py` at `6302b12`, 6,096 B,
`--mode review`) put to `google/gemini-3.7-flash`. The answer key expects zero
findings. It emitted exactly one, and the one is real: the metadata oracle stats
`EXISTING[0]` unconditionally, and if that entry is `/etc/shadow` the stat
succeeds — directory search permission is all `stat()` needs — so a working jail
is reported as leaking. The three numbers the key asks for: **emitted 1, genuinely
new and real 1, inventions 0.** It reported neither of the two pre-registered
false positives.

## Evidence

Run `logs/2026-09-03T02-36-31Z`, `context_bytes` 6096, `finish_reason` stop. The
finding, verbatim in substance: `stat_outside` uses `EXISTING[0]`; if
`OXBOX_EXISTING_PATHS` has `/etc/shadow` first, `os.stat` succeeds where `open`
would not, `probe()` treats success as a leak, and the suite exits 1 "even when
the sandbox is functioning properly".

Verified against the pin and the launcher, then against a real run:

- `git show 6302b12:jailtest.py` lines 93–94 and 134: the oracle is
  `os.stat(EXISTING[0])`, expected blocked.
- `git show 6302b12:oxbox` lines 93–107, `sensitive_paths()`: home-relative
  paths first, then the project `.env`, then `/etc/shadow` on non-Darwin; line
  343 filters by `os.path.lexists` preserving order. So `/etc/shadow` is first
  exactly when no home-relative entry and no `.env` exists.
- Same file, lines 190–197: bubblewrap `--ro-bind`s `/etc` when present, so
  `stat("/etc/shadow")` inside the jail succeeds at any uid.
- The CI log for the latest green run (`gh run view 33592372394`, job
  `jail (ubuntu-latest)`, 2026-09-02T04:51Z):

  ```
  [PASS] fs read: ~/.docker/config.json                    (FileNotFoundError)
  [PASS] fs read: /etc/shadow                              (PermissionError)
  [PASS] fs metadata: stat ~/.docker/config.json (oracle)  (FileNotFoundError)
  jail holds: 9/9 probes passed, 0 skipped
  ```

  On that runner the sensitive list is two entries long, and the oracle stats the
  docker file only because it sorts first. The Debian package smoke test in
  `release.yml` shows the identical pair. Remove `~/.docker/config.json` from the
  runner image — a choice GitHub makes, not this repo — and the oracle stats
  `/etc/shadow`, succeeds, and both workflows go red on a jail that holds.

The model's line references (`79-80`, `110`) are off by about fourteen lines
from the pin; the code it quotes is the code that is there.

## So what

This is the first non-zero middle number on the clean control, and it came from
the baseline rather than a candidate: a real, reachable defect in a 6 KB file that
MiniMax M3, Sonnet 5 and every prior human pass over it missed, found by the
cheaper of the two paid references. It also lands on the fixture's own premise.
The key says "every defect anyone has found in it has been fixed at this pin",
which was true when written and is now false, and the corpus rule says a fixture
with evidence is frozen. So the pin stays, the key's expected count stays zero
for the reason it gives — a finding is a discovery or an invention, and this one
is a discovery — and a future candidate that reports it earns a real, not a
false positive. The scoring language in the key needs no change. The file it
describes is fixed in oxbox `0090c35`: the oracle now takes the first sensitive
path outside `DAC_DEPENDENT` and skips, saying why, when there is none.

Calibration was also right: one finding, filed as a definite defect with a
failure scenario, and the scenario holds. No UNCERTAIN section, nothing padded.

No marker: this is a baseline, not a candidate.
